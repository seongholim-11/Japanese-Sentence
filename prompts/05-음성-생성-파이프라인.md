````
M4 단계를 진행해 줘. 목표는 "일본어 mp3 음성을 앱에 포함하는 것(영어 앱과 같은 방식)"이야.

# 먼저 읽을 것
- 영어 앱의 음성 스크립트 D:\personal_project\English-Sentence\scripts\generate-audio.cjs (읽기 전용 참고)와 복사된 프로젝트의 scripts\generate-audio.cjs, src\speech.ts, src\audio\manifest.ts, .env.example
- docs\02-데이터-명세와-콘텐츠-계획.md 5장(음성 합성용 텍스트 정책)

# 사실 확인 (코드 쓰기 전)
1. Google Cloud TTS Chirp 3 HD 가 일본어(ja-JP)를 지원하는지, ja-JP 음성 이름 목록을 **직접 조회**해(스크립트의 --list-voices 를 languageCode ja-JP 로 쓰도록 고쳐 실행). 지원 음성이 없으면 중단하고 대안(Neural2/Wavenet 일본어 음성 등)을 사용자에게 제시해.
2. 요금·무료 한도를 공식 문서에서 확인하고, 이 프로젝트의 총 문자 수를 `--dry-run` 으로 계산해 한도 대비 비율을 보고해.

# 작업
3. generate-audio.cjs 수정:
   - 읽을 대상(collectItems): 단어 표제어, 단어 예문, 문형 표제어·예문, 문장 정답(ja), 대화문 줄(ja), 가나 문자·예 단어, 용어집 항목 — 앱이 실제로 speak() 하는 문자열과 **정확히 같아야** 해(speech.ts·화면의 speakText 규칙과 대조 테스트를 만들어).
   - languageCode ja-JP, 음성 main/alt 를 .env(TTS_VOICE, TTS_VOICE_ALT)로. 대화문 A=main, B=alt.
   - 읽기 보정: audio-overrides.json(`{ "text": "...", "ssml": "<speak>…<sub alias=\"よみ\">表記</sub>…</speak>" }`)을 지원하고, 보정된 문구는 같은 키(`${voice}|${text}`)로 파일을 만들어 앱에서 변경 없이 찾게 해.
   - 단어 표제어 합성 기준 옵션 `--word-source=surface|reading`: 표기 기준과 읽기(가나) 기준을 둘 다 샘플로 만들어 비교할 수 있게.
   - 속도·샘플링·이어서 생성(index.json), 분당 요청 제한(영어 앱 방식)은 유지.
4. 샘플 청취(사용자와 함께): 단어 30개(한 글자 한자·동음이의어 포함), 문장 20개(다의 읽기 포함: 行った, 今日, 一人 등), 대화문 한 편을 `assets\audio-samples\` 에 만들고(.gitignore 에 포함), 어떤 파일이 어떤 문구인지 표로 정리해. 사용자가 들어 본 결과로 표기/읽기 기준과 음성 2종을 확정하게 해. 네가 직접 소리를 들을 수는 없다는 점을 분명히 하고, 청취 판단은 사용자가 해.
5. 확정 후 전체 생성(`npm run audio`), manifest 자동 생성, 누락 점검 스크립트: 앱이 읽는 모든 문구 → 파일 존재, 빈 파일·고아 파일 0, 용량 보고.
6. 앱 연결 확인: 웹(로컬)에서 단어·예문·대화문 A/B 재생이 의도한 파일을 쓰는지(재생 호출을 가로채 확인), 파일이 없을 때 기기 음성으로 대체되는지.
7. NOTICES.md·설정 > 출처·라이선스·스토어 문구에 "Google Cloud Text-to-Speech로 만든 합성 음성" 고지를 일본어 앱 기준으로.

# 주의
- 한 번 생성한 음성은 비용이 든다. 콘텐츠가 바뀌면 바뀐 문구만 다시 생성하도록 이어서 생성 기능을 활용해.
- .env 에 키를 쓰지 마(프로젝트 ID·음성 이름만). 인증은 gcloud ADC.
- 음질·발음 판단은 청취가 필요해. 네가 확인하지 못한 것은 "청취 필요"로 적어.
````
