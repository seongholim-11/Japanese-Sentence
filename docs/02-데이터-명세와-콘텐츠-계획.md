# 데이터 명세와 콘텐츠 제작 계획

> **확정 결정은 `docs/DECISIONS.md`가 우선한다.** 이 문서의 숫자·방침이 DECISIONS와 다르면 DECISIONS를 따른다.

영어 앱의 카드 구조(`Card { id, tag, front, hint, back, ex, exKo }`, 대화문 `Line { who, speaker, en, ko }`)를 일본어에 맞게 확장한다. 영어 앱에서 `hint`는 발음기호(IPA)였고, 일본어에서는 **읽기(reading)** 가 그 자리를 차지한다.

## 1. 공통 규칙

- 모든 일본어 텍스트는 **NFC 정규화**된 전각 일본어 문장부호(。、？！)를 쓴다. 숫자는 반각, 영문은 반각.
- 한국어 뜻·해석은 **자연스러운 한국어 구어체**(해요체)로, 직역투를 피한다. 영어 앱의 한국어 톤(`~했어요`, `~해 줘`)과 같은 결을 유지한다.
- 읽기(reading)는 **히라가나**로 쓰되, 가타카나 단어(コーヒー)는 가타카나 그대로 쓴다(읽기 = 표기).
- 예문 읽기(exReading)는 예문 전체를 히라가나로 적되 가타카나 외래어는 그대로 둔다. 조사 は는 は, へ는 へ, を는 を로 표기(발음 そのまま가 아니라 **표기 그대로 가나로 변환**).
- 존댓말(です・ます)을 기본으로 하고, 반말 예문은 `style: "普通"`으로 표시한다.
- 비속어·차별 표현·정치·종교 논쟁·성적 표현은 쓰지 않는다. 술·담배·폭력 낱말은 영어 앱처럼 꼭 필요한 최소한만 쓰고, 연령 등급 설문 기준(13+ 목표)에 맞춘다(결정 필요).
- 개인 이름·실제 상표·실존 인물은 예문에 쓰지 않는다(지명·일반 명사는 허용).
- 모든 id는 중복 불가. 단어 id는 `표기#읽기`(동음이의 구분). 예: `橋#はし`, `箸#はし`.

## 2. 덱별 스키마 (JSON 예시)

### 2-1. 단어 (`words`)

```json
{
  "id": "食べる#たべる",
  "tag": "동사",
  "front": "食べる",
  "reading": "たべる",
  "back": "먹다",
  "ex": "毎朝パンを食べます。",
  "exReading": "まいあさパンをたべます。",
  "exKo": "매일 아침 빵을 먹어요.",
  "level": "N5",
  "style": "丁寧",
  "blank": "食べ"
}
```

- `tag`: 명사 / 동사 / い형용사 / な형용사 / 부사 / 조사·접속 / 대명사 / 수사·조수사 / 외래어 / 기타
- `level`: `N5` | `N4` | `N3` (v1.1 이후 `N2`). **비공식 구분**.
- `blank`(선택): 예문에서 빈칸으로 만들 **활용된 형태의 부분 문자열**. `ex.includes(blank)`가 참이어야 하고, 한 번만 나와야 한다. 없으면 빈칸 문제는 출제하지 않는다.
- `front`가 가나뿐이면 `reading`은 `front`와 같다. 이 경우 카드에 읽기를 따로 보여 주지 않는다.
- 동사는 사전형(辞書形)을 `front`로 하고, 활용형 설명은 문형 덱에서 다룬다.

### 2-2. 문형·표현 (`patterns`) — 영어 앱의 구동사 자리

```json
{
  "id": "〜ておく",
  "tag": "문형",
  "front": "〜ておく",
  "reading": "〜ておく",
  "back": "(미리) ~해 두다",
  "note": "동사 て형 + おく. 준비·방치의 뜻",
  "ex": "旅行の前にホテルを予約しておきます。",
  "exReading": "りょこうのまえにホテルをよやくしておきます。",
  "exKo": "여행 가기 전에 호텔을 예약해 둬요.",
  "level": "N4",
  "style": "丁寧",
  "blank": "しておき"
}
```

- 문형은 접속 규칙(`note`)을 한 줄로 쓴다. 인사·관용 표현(お疲れ様です, よろしくお願いします)도 이 덱에 둔다(`tag: "표현"`).

### 2-3. 문장 (`sentences`)

```json
{
  "id": "これはいくらですか。",
  "tag": "한국어 → 일본어",
  "front": "이거 얼마예요?",
  "ja": "これはいくらですか。",
  "reading": "これはいくらですか。",
  "note": "いくら = 얼마, 가격을 물을 때",
  "style": "丁寧",
  "level": "N5"
}
```

- `front`는 한국어, 정답은 `ja`/`reading`. 영어 앱의 문장 덱처럼 "앞에서 배운 단어·문형을 활용"하도록 `uses: ["いくら#いくら"]` 같은 참조를 둘 수 있다(선택, 검수에 도움).

### 2-4. 대화문 (`dialogues`)

```json
{
  "id": "cafe",
  "title": "카페에서 주문하기",
  "expressions": ["お願いします", "〜でお願いします"],
  "lines": [
    { "who": "A", "speaker": "店員", "ja": "いらっしゃいませ。ご注文はお決まりですか。", "reading": "いらっしゃいませ。ごちゅうもんはおきまりですか。", "ko": "어서 오세요. 주문 정하셨나요?" },
    { "who": "B", "speaker": "私", "ja": "アイスコーヒーをひとつお願いします。", "reading": "アイスコーヒーをひとつおねがいします。", "ko": "아이스커피 하나 주세요." }
  ]
}
```

- 6줄, A/B 교대. `speaker` 이름은 일본어 직함·이름(店員, 友達, 山田さん)처럼 일반적인 것.
- `expressions`는 단어·문형 덱에 있는 표현이거나, 없으면 `expressions.ts` 용어집(뜻·예문)에 항목을 만든다. **영어 앱에서 겪은 문제**: 덱에 없는 표현이 설명 없이 칩만 남음 → 검증 스크립트로 전부 설명이 있는지 확인한다.

### 2-5. 가나 (`kana`) — 신규

```json
{ "id": "あ", "tag": "히라가나·청음", "front": "あ", "reading": "a", "back": "아", "ex": "あさ", "exReading": "あさ", "exKo": "아침" }
```

- 한글 독음(`back`)은 **대략적인 안내**일 뿐임을 앱 안에 한 줄 표기(예: う, ふ, つ, ん은 한글로 정확히 옮길 수 없음).
- 구성: 히라가나 청음 46 + 탁음·반탁음 25 + 요음 33 = 104, 가타카나 동일 104 → 약 208장(제안). 가타카나 카드는 외래어 예(コーヒー)를 쓴다.
- 쓰기 순서(획순) 애니메이션은 v1 범위 밖.

## 3. 수량·레벨 목표 (제안)

| 덱 | v1.0 (확정) | 이후 | 비고 |
| --- | --- | --- | --- |
| 가나 | ~208 | – | 정확성 검수가 쉬워 첫 번째로 완성 |
| 단어 | ~2,500 (N5 ~700 + N4 ~800 + N3 ~1,000) | – | 빈도·일상 회화 중요도 우선 |
| 문형·표현 | ~200 | – | N5~N3 필수 문형 + 인사·관용 표현 |
| 문장 | ~800 | – | 단어·문형을 섞어 쓰는 회화 문장 |
| 대화문 | ~80 | – | 상황 6줄 |

음성 mp3 개수 추정: 단어 2,500×2(표제어+예문) + 문형 200×2 + 문장 800 + 대화문 480줄 + 가나 약 208×2 ≈ 7,100개, 문자 수는 대략 7만~12만 자, mp3 용량 약 40MB 안팎(영어 앱 29.6MB/5,223개 기준 추정). 무료 한도 이내일 가능성이 높지만 **확인 필요**: 요금·무료 한도는 Google Cloud 안내를 직접 볼 것.

## 4. 콘텐츠 제작 파이프라인

```
① 후보 목록 만들기 (레벨·빈도·상황 기준)  →  ② 1차 생성(AI, 스키마 JSON)  →  ③ 자동 검증(스크립트)
→ ④ 읽기 자동 대조(형태소 분석기)  →  ⑤ 교차 검수(다른 모델/사람)  →  ⑥ 수정 반영  →  ⑦ 최종 고정(freeze) → ⑧ 음성 생성
```

### ③ 자동 검증 스크립트 (영어 앱의 검증 스크립트 방식을 따른다)

- 스키마: 필수 필드, 타입, 허용 값(`tag`, `level`, `style`).
- 중복: id 중복, 같은 표기+읽기 중복, 같은 예문 중복.
- 문자: 일본어 필드에 한국어/영어/전각 공백/제어문자 섞임 없음(예외: 외래어 로마자는 쓰지 않는다). 한국어 필드에 한자·가나 섞임 없음(예외: 용어 설명용 `〜ておく` 인용은 note에서만 허용).
- `blank`: `ex.includes(blank)` 이고 한 번만 등장.
- `reading`/`exReading`: 가나(+장음 ー, 문장부호)만 포함. 한자가 남아 있으면 오류.
- 길이: 예문 일본어 8~40자 권장, 대화 한 줄 40자 이하.
- 표현 설명: 대화문 `expressions`가 단어·문형 덱 또는 용어집에 모두 있는지.
- 금지어 목록 스캔(비속어·민감어), 실제 상표·인명 스캔.

### ④ 읽기 자동 대조

- 형태소 분석기(Node의 `kuromoji` 등 — **사용 가능 여부는 프로젝트에서 확인**)로 표기의 읽기를 만들어 `reading`/`exReading`과 비교한다. 불일치 목록은 사람이 확인(다의 읽기로 인한 정상 불일치가 있다).
- 조사 は/へ/を, 장음, 촉음, 가타카나 외래어 표기 차이를 정규화한 뒤 비교.

### ⑤ 교차 검수

- 생성한 모델과 **다른 모델/에이전트**가 일본어 자연스러움, 문체 일관성, 한국어 뜻 정확성을 검수(`prompts/06-교차검수.md`).
- (확정 사항 아님·선택) 일본어 원어민 또는 상급 학습자가 샘플(10~20%)을 보면 정확도가 더 오른다.
- 검수는 AI 교차검수로 확정(원어민 검수 없음, DECISIONS #17). 원어민 확인이 필요하다고 표시된 항목은 목록으로 남겨 출시 후 신고·수정에 쓴다.
- 모든 지적은 `reports/review-<덱>-<날짜>.md`에 기록하고, 수정 후 재검증.

## 5. 음성 합성용 텍스트 정책

- 문장·대화문: `ja`(표기) 기준 합성이 기본. 다의 읽기로 틀리는 문구는 **읽기 보정 목록**(`audio-overrides.json`: `{ "text": "...", "ssml": "..." }`)으로 SSML `<sub alias="かな">` 등으로 고친다.
- 단어 표제어: 표기 기준 합성과 읽기(가나) 기준 합성을 20~30개 샘플로 비교 청취한 뒤 선택한다(예상: 한 글자 한자·동음이의어는 읽기 기준이 안전).
- 대화문: A는 음성 1, B는 음성 2(영어 앱과 동일). 음성 이름은 `list-voices`로 `ja-JP` Chirp 3 HD 목록을 확인해 고른다.
- 키: 영어 앱과 같이 `${voice}|${text}` 해시로 파일명을 만든다(보정 텍스트도 같은 규칙).

## 6. 영어 앱에서 얻은 교훈 (그대로 적용)

1. 저장값 검증은 필드별로(한 필드가 깨져도 전체가 죽지 않게). 새 스키마 필드를 늘릴 때마다 sanitize와 검증 스크립트에 넣는다.
2. 퀴즈 오답 보기는 **같은 뜻이 겹치지 않게**, 정답이 문장에 이미 나오지 않게.
3. 큰 글자·작은 화면에서 고정 높이를 피하고 minHeight를 쓴다. 후리가나 줄이 더해져 카드가 높아지므로 특히 주의.
4. 라이선스 전문은 앱 안에서 볼 수 있어야 한다.
5. 웹 버전은 GitHub Pages에 올리지 않고, 방침·지원 페이지만 올린다.
6. 실기기(무음 모드·비행기 모드·알림)는 TestFlight에서 확인한다.
